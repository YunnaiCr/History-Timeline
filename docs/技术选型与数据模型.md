# 历史事件线：技术选型与数据模型（v0.1）

## 1. 结论先行

**技术栈：Tauri 2 + React 19 + TypeScript + Vite，状态用 Zustand，本地数据用 SQLite（tauri-plugin-sql），时间轴自己用 DOM/Canvas 混合渲染，不套现成的 Gantt 库。**

| 层 | 选择 | 理由 |
|---|---|---|
| 桌面壳 | Tauri 2 | WebView2 随 Win10/11 自带，安装包 ~10MB 级；Rust 侧可做文件读写/SQLite；比 Electron 轻一个数量级 |
| UI | React 19 + TypeScript | 生态最大，拖拽/虚拟滚动库齐全 |
| 构建 | Vite | 启动快，与 Tauri 天然配对 |
| 状态 | Zustand | 轻，适合"筛选条件 + 视口 + 选中项"这类全局状态 |
| 存储 | SQLite（`tauri-plugin-sql`）或直接存 JSON 文件 | 数据量小（几千条）JSON 足够；要全文搜索/多档位再上 SQLite |
| 时间轴 | 自研（DOM + Canvas 刻度） | 见第 3 节，没有现成库能同时满足"收纳展开 + 无限长度 + 双轴筛选" |

> 已按你的选择直接上 Tauri 2 桌面版；主开发路径仍是 `npm run dev` 浏览器热更新，
> 只是最终产物是 exe。M0 的 UI 与时间核心和 Tauri 无关，套壳在 M5 完成。

## 2. 为什么不用现成的时间轴/Gantt 库

候选：vis-timeline、dhtmlx-gantt、frappe-gantt、Recharts/echarts 时间轴。

- **vis-timeline**：最接近，支持横向拖拽缩放、分组；但它的"分组折叠"是整行折叠，不是"同一个时间点内事件收纳成一个圆点/卡片群"；它的缩放是固定几档（毫秒→年），做"世纪级 → 日级"的大跨度需要改源码；样式是旧式 DOM，导航非常重。做过几百节点后会卡。
- **Gantt 类**：核心是"任务条有起止时间"，而历史事件多数是**点事件**，硬套会别扭；而且它们的"层级"是任务分解，不是"时间节点收纳"。
- **结论**：这类软件的核心难点正好是这些库最弱的地方，自研 DOM 渲染反而是最省事的。不用 Canvas 全画，因为你要点击/拖拽/悬浮卡，DOM 更好做交互；只在刻度尺用 Canvas。

## 3. 四个目标对应的技术方案

### 3.1 左右滚动 + 拖动
- 外层 `div` 用原生滚动（`overflow-x: auto`），滚动条换成自绘的"迷你地图"缩略轴。
- 拖动 = 在容器上监听 `pointerdown/move/up`，改 `scrollLeft`（惯性可选）。`pointer` 事件一套代码同时支持鼠标和触摸/触控笔，Win 平板也能用。
- 缩放用 `wheel` + `ctrlKey`（触控板双指捏合同样触发），锚定鼠标位置换算成时间，避免缩放时画面跳。
- **不要用 transform 平移整个时间轴**——无限长度下 DOM 会爆。用"虚拟滚动"：只渲染视口内的节点（见 3.2）。

### 3.2 时间节点收纳展开 + 不限长度
这是设计的核心，建议模型化成三层：

```
Timeline（时间轴，可多条并行，如"中国史"/"世界史"）
└── Cluster（收纳组：同一时间窗口内 N 个事件的合并显示，如"1911–1912"）
    └── Event（单个事件，有点时间，或起止区间）
```

- **无限长度**靠两层手段：
  1. **虚拟化渲染**：只渲染视口 ±1 屏的节点，100 万事件也不卡（DOM 只保留几百个）。
  2. **两级缩放**：`zoom = 像素/天`，从 0.0001（一个世纪一屏）到 20（一天一屏）。不同 zoom 下切换粒度（千年→世纪→十年→年→月→日）。
- **收纳展开**有两种实现，建议**都做**：
  - **自动收纳**：当两个节点的像素间距 < 阈值（如 24px）时，自动合并成一个"簇"，显示 `N ↑` 徽标；点击/滚轮放大后自动拆开。这是"展开"的默认体验。
  - **手动收纳**：用户可框选事件 → "收进分组"，分组有名字和颜色（如"辛亥革命"），在低缩放级别显示为一张卡片，点开在下方展开子项（或浮层）。数据上就是 `Event.groupId`，用平表 + 自关联，不用嵌套树。
- 事件本身支持**点事件**和**区间事件**（起止），区间在低缩放时显示为条，高缩放时两端可拖。

### 3.3 类别（Category）+ 筛选
- 类别 = **单值、必填**（每条事件只属于一个类别，如"政治/经济/科技/文化"），这是主轴。
- 类别定义：`id, name, color, icon, order`，存独立表，用户可增删改、调色。
- 筛选：顶部一排类别 chip，多选切换显隐。**渲染时对类别过滤**，而不是删除 DOM。
- 建议把"流水线"做成：`原始数据 → 类别过滤 → 标签过滤 → 时间窗裁剪 → 虚拟化 → 渲染`，全是纯函数，好测试。

### 3.4 标签（Tag）+ 筛选
- 标签 = **多值、可选**，与类别**完全独立**（同一个事件可以既是"政治"又有 `#民国` `#留学生` 两个标签）。
- 数据结构：`Event` 表 + `Tag` 表 + `EventTag` 关联表（SQLite）；JSON 方案就是数组。
- 筛选逻辑建议支持 `AND` 与 `OR` 两种模式（UI 上一个切换按钮）：`AND` = 同时具备所选标签；`OR` = 任一即可。默认 OR 更符合直觉。
- 标签建议有**自动完形**（输入时提示已有标签），避免"民国/中华民国"分裂成两个标签。

## 4. 数据模型（SQLite 版）

```sql
CREATE TABLE timeline (
  id          TEXT PRIMARY KEY,
  name        TEXT NOT NULL,
  color       TEXT
);

CREATE TABLE category (
  id          TEXT PRIMARY KEY,
  timeline_id TEXT NOT NULL REFERENCES timeline(id) ON DELETE CASCADE,
  name        TEXT NOT NULL,
  color       TEXT NOT NULL,
  sort_order  INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE event (
  id           TEXT PRIMARY KEY,
  timeline_id  TEXT NOT NULL REFERENCES timeline(id) ON DELETE CASCADE,
  category_id  TEXT NOT NULL REFERENCES category(id),
  title        TEXT NOT NULL,
  summary      TEXT,              -- 简述
  detail       TEXT,              -- 长文/Markdown
  -- 时间：用"儒略日 × 10"或"天数偏移"存为整数，避免时区问题
  start_day    INTEGER NOT NULL,  -- 相对公元 1 年 1 月 1 日的天数，可为负（公元前）
  end_day      INTEGER,           -- NULL = 点事件
  fuzzy_start  TEXT,              -- 原始文本，如 "约公元前1046年"
  importance   INTEGER DEFAULT 1, -- 1..5，控制收敛/展开阈值
  group_id     TEXT REFERENCES event_group(id) ON DELETE SET NULL,
  created_at   TEXT NOT NULL,
  updated_at   TEXT NOT NULL
);

CREATE TABLE event_group (          -- 手动收纳组
  id          TEXT PRIMARY KEY,
  timeline_id TEXT NOT NULL REFERENCES timeline(id) ON DELETE CASCADE,
  name        TEXT NOT NULL,
  color       TEXT,
  summary     TEXT
);

CREATE TABLE tag (
  id   TEXT PRIMARY KEY,
  name TEXT NOT NULL UNIQUE,
  color TEXT
);

CREATE TABLE event_tag (
  event_id TEXT NOT NULL REFERENCES event(id) ON DELETE CASCADE,
  tag_id   TEXT NOT NULL REFERENCES tag(id)  ON DELETE CASCADE,
  PRIMARY KEY (event_id, tag_id)
);

CREATE INDEX idx_event_time ON event(timeline_id, start_day);
```

关键点：
- **时间统一存整数天数**（相对一个基准日），显示层再按粒度格式化。历史日期有大量"约公元前 / 公元后"问题，用 `fuzzy_start` 保留原文本，数值用于排序定位。
- **类别用外键，标签用多对多**——这样"类别必须唯一"由结构保证，不会出现一个事件挂两个类别。
- `importance` 很有用：低缩放时只显示重要事件，避免一开始就密密麻麻。

## 6. 在 Windows 上要注意的

- **WebView2**：Win11 自带；Win10 较新版本一般有，老机器需装运行时（微软官方 Evergreen 离线包）。如果要低版本 Win10 兼容，考虑 Electron 保底。
- **高 DPI**：时间轴按 CSS 像素计算即可，但 Canvas 刻度要乘 `devicePixelRatio`，否则 125%/150% 缩放下刻度发虚。
- **中文输入**：编辑弹窗里注意 `compositionstart/end`，别在拼音输入过程中触发快捷键。
- **打包**：Tauri 2 用 `cargo tauri build`，需要 Rust 工具链 + VS Build Tools（C++ 桌面开发）。首次编译慢，但之后增量很快。
- **数据存放**：用 `app_data_dir()`（`%APPDATA%\<identifier>`），不要存程序目录——Program Files 无写权限。
- **备份/同步**：设计成"单文件数据库 + 导入导出 JSON"，方便挪到 OneDrive 或 Git。

## 7. 备选与代价

| 方案 | 适合 | 代价 |
|---|---|---|
| Tauri 2（已采用） | 要轻、要 Win 原生 exe | 需 Rust 工具链；首次配置比 Electron 麻烦 |
| Electron | 团队只想用 JS，要最稳的兼容 | 安装包 ~100MB，内存高 |
| 纯 Web + PWA | 先验证想法 | 没有本地文件持久化优势，离线依赖浏览器存储 |
| PowerToys/AutoHotkey 等脚本 | 不推荐 | 做不了复杂交互 |

**建议：功能验证阶段继续用浏览器热更新（`npm run dev`）最快；等 M2 收纳交互定稿后再集中处理 Tauri 打包。** 这样 90% 的时间花在真正难的地方（时间映射、收纳、筛选），而套壳只在最后。

## 8. 本机沙箱限制（只影响我这边跑命令，不影响你）

DSH 沙箱禁止进程 spawn，`vite`/`esbuild` 一启动就 `spawn EPERM`（报错会伪装成 `failed to load config`）。
所以我在 `app/` 里额外放了不依赖打包器的预览路径：`npm run build:m0`（tsc 编译）+ `npm run preview:m0`（零依赖静态服务器）。
你在正常终端里不会遇到这个问题，直接 `npm run dev` 即可。
